# Statistical contract

Every model or study unit follows this contract. A unit is covered if the work
queue marks it PRE, or if it produces or changes a number a model serves (a
projection, availability, playoff odds, trade value, a usage share, a decision
threshold). "Not applicable, because ..." is an answer. Silence is not.

This page is the entry point. The eight base rules live in one place,
[`docs/evidence/STATS-METHOD.md`](evidence/STATS-METHOD.md) (unit S-00, #154),
and are linked here, not copied. This page adds three rules that file does not
have (9-11), the pre-registration template, and the machine check that
enforces rule 1.

`89f69b3b`. Evidence: `docs/tdd/2026-09-23-stats-contract-prereg-order.tdd.md`.

## Rule 9. Clustered intervals

Player-weeks are not independent. One player's weeks share his role and talent,
and one week's players share weather, game script and slate. Resampling
player-weeks one at a time treats correlated rows as separate evidence and makes
the interval too narrow. Brill, Yurko and Wyner (arXiv:2406.16171, 2024) found
NFL bootstraps reaching about 60% real coverage at 90% nominal for this reason.
The standard fix is to resample whole clusters (Cameron, Gelbach and Miller,
*Journal of Business & Economic Statistics* 29(2), 2011, for two-way clustering).

- Resample the unit that is independent: **player** when one player carries many
  rows (projection error), **week** when one week carries many decisions
  (league-wide calls), and **both** for start/sit pairs.
- State the clustering in the pre-registration and beside every interval, e.g.
  "90% CI, player-clustered".
- Reuse the producers. `pairedBootstrapDiff` resamples whole groups when `groups`
  is passed. `gradeDecisions` returns `ci90.player` and `ci90.week` together.
  The start/sit gate's verdict needs both bounds (`baselineGateVerdict`, G1 and G2).
- An i.i.d. interval can be shown next to the clustered one. It never decides.

## Rule 10. Forward-only grading for anything an LLM touched

A language model's training data can include the seasons we would replay it on.
So a "historical" grade of LLM output partly measures memory, not skill. This is
look-ahead bias (Glasserman and Lin, "Assessing look-ahead bias in stock return
predictions generated by GPT sentiment analysis", arXiv:2309.17322, 2023; Sarkar
and Vafa, "Lookahead bias in pretrained language models", SSRN, 2024). The same
applies when an LLM agent picked a feature or a threshold after reading results.

- **Touched** means an LLM wrote the number, scored an input (news, injury text),
  chose the candidate (a trade, a waiver add, a feature), or wrote the rule after
  seeing any of the data it is graded on.
- Grade such output only on games played after **both** the model's training
  cutoff and the date the output was produced and committed. A replay on earlier
  seasons is reported as an anecdote, never as a verdict.
- The pre-registration names the model and its cutoff. If the cutoff is unknown,
  it says so and uses the output's commit date as the cutoff.
- A 2025 look taken to choose an LLM-proposed change is a ledger row (rule 2) and
  makes that change's 2025 grade in-sample.

## Rule 11. Win rate against ESPN, graded over history

Rule 6 already requires the decision win rate against the dumb baseline (start
the highest projection, add the highest-projected free agent, offer fair value).
A user also has ESPN's projection on screen, so a start/sit claim is also graded
against ESPN wherever ESPN has a number.

- ESPN's weekly projection is stored in `league_roster_snapshots.projected_points`
  (ESPN `statSourceId` 1), written by `scripts/collect-roster-snapshots.mjs:113`
  (table from `server/migrations/058_league_roster_snapshots.js`). It exists
  only for **rostered players, from 2026-09-18 on**. Where it has no number,
  write "vs ESPN: no number (before 2026-09-18, or unrostered)". Never fill it with
  a stand-in.
- Historical, not one week (Nick, 2026-09-22): a start/sit claim is graded by
  walk-forward as-of replay over several past seasons against the real baselines
  a user has. It uses the HX-01 harness once that is merged. It is not merged on
  `89f69b3b`: `git grep -n HX-01` finds only a prereg addendum. A one-week
  comparison is an anecdote.
- Report the win rate with its player- and week-clustered interval (rule 9) and,
  on a decline, its MDE (rule 4).

## Rule 1, enforced: `scripts/check-prereg-order.mjs`

The check pairs each results file with its pre-registration. It fails if the
results file's first commit does not descend from the prereg file's first
commit.

**Name your files so they pair.** Put both in the same directory:

- prereg: `<stem>-preregistration.md` or `<stem>-prereg.md`. Addenda are
  `<stem>-prereg-addendum-N.md` or `-amendment-N.md`, and the earliest committed
  file of the group is the anchor.
- results: `<stem>.md`, `<stem>-result.md`, `<stem>-results.md`,
  `<stem>-output.json` or `<stem>-findings.md` (any extension).
- A file in another directory (for example the `docs/tdd/*.tdd.md` evidence
  file, which is never paired by name because its audit section comes before
  the first test) opts in with the line `<!-- prereg: docs/evidence/<date>/<stem>-preregistration.md -->`.
  If that path was never committed, the check fails.

**Run it** before you push, on your branch, where each commit is still separate:

```
npm run check:prereg-order                       # docs/evidence/ and docs/tdd/
node scripts/check-prereg-order.mjs --prefix docs/evidence/2026-09-23/ --strict
```

Exit 0 means ok, 1 a violation, 2 a shallow clone (history not visible, so no
verdict), 3 any other error. `--json` prints the report.

**What CI proves, and what it does not.**

- `test/check-prereg-order.test.js` runs in `npm test` on every PR. It builds
  throwaway fixture repos and checks that the script fails when the results come
  first and passes otherwise.
- The same test also scans this repository, but only with full history. CI
  checks out at depth 1, so that case is skipped there with a reason.
  Follow-up: `fetch-depth: 0` in `.github/workflows/ci.yml` would make CI scan
  each PR branch. That file needs a grant.
- `main` is squash-merged, so on `main` a PR's prereg and results share one
  commit. The check reports that as `same commit` and passes it, because the
  order is not provable from `main`. `--strict` fails it.

## Pre-registration template

Copy this into `docs/evidence/<date>/<stem>-preregistration.md`. Commit it, alone,
before any command that prints a number from the test.

```markdown
# <stem>: pre-registration

Unit: <ID>. Plan item: <n>. Tree: origin/main <sha>. Date: <YYYY-MM-DD>.

1. Hypothesis (one sentence):
2. Metric and sign convention (default candidate - incumbent; negative MAE change = better):
3. Split: fit seasons / held-out season / weeks / population (positions, startable threshold):
4. Incumbent (the app as served, found by: <command>) and dumb baseline (rule 6):
5. vs ESPN (rule 11): weeks where league_roster_snapshots has a number, or "no number":
6. Historical replay: seasons, walk-forward as-of, harness (HX-01 or named stand-in):
7. Interval: level, clustering (player / week / both), producer (rule 9):
8. Family and correction: family name, m so far, BH q (rule 3); ledger row id to add (rule 2):
9. MDE at 80% power from the expected SE (rule 4):
10. Ship rule, including the 2026 forward check and what ships default-off (rule 5):
11. Replay configuration: roleRecency, kOverride absent, k control (rule 7):
12. LLM involvement: none / what it touched, model, cutoff, forward-only window (rule 10):
13. Literature (2-3 sentences, cited):
14. What would make us stop early (none, or the always-valid rule used):
```

The result file is `<stem>-results.md` in the same directory, or it carries the
`<!-- prereg: ... -->` marker.
