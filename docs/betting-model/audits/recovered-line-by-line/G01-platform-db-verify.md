## G01-platform-db#3 — VACUUM INTO snapshot before every migration can refuse to boot when disk headroom is short

File read in full: `server/db/index.js` (95-148 covers the mechanism), `server/db/migrate.js` (full, 81 lines).

- `server/db/index.js:121` — `const SNAPSHOT_HEADROOM_BYTES = 2 * 1024 ** 3;` confirmed 2 GiB constant.
- `server/db/index.js:124-148` — `assertRoomForSnapshot` computes `needed = statSync(databasePath).size + SNAPSHOT_HEADROOM_BYTES` and throws a hard error (not caught anywhere in the call chain) when `free < needed`.
- `server/db/index.js:95-108` `backupBeforeMigration` calls `assertRoomForSnapshot` unconditionally whenever there is any prior non-legacy migration history (`prior` > 0), then does `VACUUM INTO`.
- `server/db/migrate.js:33-45` `runMigrations` calls `backupBeforeMigration` whenever `pendingCount > 0 || repairs.length` — i.e. for ANY pending migration file, no matter how trivial (an index-only migration triggers the same full-DB snapshot as a large data migration). This is called unconditionally from `server/index.js:21` (`await runMigrations()`), with no try/catch around it in `server/index.js`, so a thrown `assertRoomForSnapshot` error is an uncaught rejection that kills the boot before `app.listen` ever runs — a genuine refuse-to-boot outage, not merely a slow migration.
- `server/db/index.js:91-93` (comment) confirms snapshots are "never pruned automatically."
- Live filesystem checks (read-only stat/ls/df, no writes): `server/data.sqlite` = 11,694,727,168 bytes (~10.89 GiB); `server/data.sqlite.pre-migration-2026-09-11T00-21-58-169Z.bak` = 9,788,506,112 bytes (~9.11 GiB, reader's "9.8 GB" — with the byte value 9,788,506,112 that actually rounds to 9.11 GiB / 9.79 GB depending on GB vs GiB convention, consistent with the reader's figure using decimal GB). `server/migrations/024_candidate_findings.js` through `035_alt_spread_capture.js` exist and are dated by the surrounding `.bak` filename timestamp of 2026-09-11, consistent with "migrations 024-035 applied 2026-09-09..09-11".
- Disk free space: `df -k` on the volume containing the repo shows **68.09 GB available**, not the reader's cited "~74.5 GB free." This is a real discrepancy in the reader's supporting evidence (likely measured at a different, earlier moment, or the machine's disk usage has shifted since — normal on a system with an actively growing 11+ GB DB and other work). Recomputing the reader's own conclusion with the correct, lower free-space figure (68 GB) against a required ~13.7 GB snapshot (current 11.69 GB DB + 2 GiB headroom) still yields "about five more migrations" as a rough order of magnitude (68/13.7 ≈ 5), and since the DB is actively growing (+1.9 GB in the two days between the cited `.bak` and today), the true number of remaining migrations before refusal is more likely fewer than five, not more. So correcting the reader's stated free-space number does not weaken the claim; if anything the risk is slightly closer than the reader estimated.

**Verdict: claim stands**, with one minor correction to the reader's supporting numbers (free space is ~68 GB now, not ~74.5 GB) that does not change the substance or severity of the defect: the mechanism genuinely can refuse to boot the server, is unconditionally on the migration path, has no exemption for trivial/small migrations, and snapshots are never pruned. P2 (boot-time refusal contingent on future migrations + disk state, not an active bug today) is the appropriate severity, not P1 — there is no evidence the condition is imminent or has fired.
