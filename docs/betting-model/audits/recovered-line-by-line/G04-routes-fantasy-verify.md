## #17 — server/routes/drafts.js:328, mock drafts invisible in listings — CONFIRMED, P2

- drafts.js read in relevant ranges (1-60, 300-400). `draftAccess()` (39-49) explicitly documents and correctly handles `league_row_id IS NULL` for per-draft routes (comment: "A mock draft has no league_row_id... Access to a leagueless draft is scoped by draft_team_ownership instead").
- `GET /` at drafts.js:326-331 (the listing endpoint, matches cited line 328's JOIN):
  ```
  FROM drafts d JOIN league_memberships lm ON lm.league_id = d.league_row_id AND lm.user_id = ?
  ```
  This is an INNER JOIN keyed on `d.league_row_id`; since SQL `NULL = anything` is never true, any draft with `league_row_id IS NULL` (i.e., every mock draft, by the design documented three lines away in the same file) is unconditionally excluded from this result set.
- POST `/` (drafts.js:328-345 region / actual 328 onward) confirms mock-draft creation path never requires or collects `league_row_id`; client/src/pages/Drafts.tsx confirmed (read lines 1-40): form state has no `league_row_id` field, only `name, type, team_count, rounds, my_slot, ranking_set_id, pick_seconds`.
- Read-only DB query (`node:sqlite`, `readOnly:true`) against `server/data.sqlite`:
  ```
  SELECT id, type, league_row_id FROM drafts ORDER BY id
  ```
  returned exactly: mock/NULL for ids 4,5,6,10,11,12,13,14,15,16,21 (11 rows) and live/non-null for ids 17,18,20,22 (4 rows) — an exact match to the claim's "11 of 15 drafts are type 'mock' with league_row_id NULL (ids 4,5,6,10,11,12,13,14,15,16,21)".
- Confirmed propagation: client/src/pages/Home.tsx:19,54 and client/src/components/SidePanel.tsx:6-8 both consume `useApi('/drafts')` the same way Drafts.tsx does, so the same 11 drafts are invisible on Home and the SidePanel too, exactly as claimed.
- Checked the "related hazard" at line ~382 (`Number(league_row_id)`): tested directly with a throwaway in-memory `node:sqlite` DB — `Number(undefined)` (what you get when the key is absent, as in the real mock-draft form) binds as SQL NULL (matches the observed real data), but `Number(null)` (what you'd get if a caller explicitly sent `league_row_id: null`) binds as integer `0`, not NULL. This is real but is a *secondary*, currently-latent hazard — the actual UI never triggers it since it omits the key entirely rather than sending `null`. The reader correctly hedged this as "Related hazard" rather than folding it into the primary claim, so it doesn't inflate the main defect.
- Conclusion: exactly as claimed and independently reproduced against live data. A user who runs mock drafts (11 of their 15 total drafts) loses all of them from every list surface once they navigate away, with no path back except memorizing/bookmarking the post-create URL. This is a real, currently-triggered UX defect affecting decisions/records the user tracks. **Not refuted, P2 is appropriate** (severe within its scope, but a navigation/discoverability bug rather than data loss or money-affecting — the drafts still exist and are reachable by direct URL/id).

## #19 — server/routes/leagues.js:232, raw ESPN cookies spread into `/data` JSON — CONFIRMED, P2

- leagues.js read across 1-30 and 210-240. Confirmed `r.get('/:id/data', ...)` (leagues.js:227-232) runs `assertLeagueMember(req.auth.userId, req.params.id)` (line 228) then `row('SELECT * FROM leagues WHERE id = ?', ...)` (229) then `res.json({ ...lg, payload: ... })` (232) — `lg` is a `SELECT *`, so it necessarily includes the raw `espn_s2` and `swid` columns, which get spread verbatim into the response for **any** member of the league (not just the commissioner who connected the ESPN account).
- Confirmed via the file's own header comment (leagues.js:11-21, read in full) that the authors were already aware `/:id/data` is where raw cookie exposure matters ("letting one account read another's ESPN/Sleeper cookies via /:id/data") — but the fix they describe adds only *membership* gating, not field redaction, so a legitimate co-member still receives the raw session cookie. The comment does not claim the payload itself is scrubbed, and the code (`{ ...lg, ... }`) is not scrubbed — a real remaining gap.
- Confirmed `/api/leagues` mount IS gated with `...legacyAuthenticated` (server/index.js:90 — `app.use('/api/leagues', ...legacyAuthenticated, leaguesRouter);`), so unlike claim #15's routes this one does require a valid bearer session — the exposure is to an authenticated fellow league member, not to the open internet, which is a meaningfully smaller blast radius than claim #15.
- Confirmed client usage: client/src/pages/MyTeam.tsx:27 calls `useApi('/leagues/${active.id}/data')` on every My Team page load, and only reads `lg?.payload` (lines 37, 40) — the raw `espn_s2`/`swid` fields are never used by the client, so this is pure unnecessary exposure with no functional reason to include them in the payload sent to the browser.
- Conclusion: exactly as claimed. A real, live-reachable route (loaded on every normal My Team visit, not a rare edge case) puts a live ESPN session credential into the browser's network response/JS heap for any league member, unused by the client, which is meaningful exposure if that browser is later compromised (XSS, shared/borrowed device, browser extension, or — per Nick's own memory notes on phone pairing — over the tunnel to a paired phone). **Not refuted, P2 is appropriate** — real credential-hygiene defect with a real trigger path, but bounded to already-authenticated league members rather than the general public, so P1 would be an overstatement.
