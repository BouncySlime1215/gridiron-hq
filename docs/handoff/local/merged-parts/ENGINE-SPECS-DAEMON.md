## ENGINE-00b: the always-on engine daemon

| ID | plan item | goal | files (file:line on origin/main) | acceptance | deps |

| ENGINE-00b-a | ALWAYS LEARNING "Engine daemon" + three speeds | A separate process that **never runs inside the web server**. **Each tick** (default every 10 min; `--interval` accepts 300-900 s): (1) run ENGINE-00a's backfill adapters **incrementally** from a per-source watermark. The sources are league_transactions_raw (moves, offers, accept/decline/veto), league_roster_snapshots (lineups), trade_outcomes (offers sent), news_items + nfl_news_signals, game_lines, nfl_injuries, and chat-store **counts/rates only**. The daemon reads the tables the refresh loop fills and **never calls ESPN itself** (one fetcher per source). (2) Append new events, then dispatch the `onEvent` learners per event, each with a time budget (default 2 s). A learner that throws or times out is recorded against that learner and never swallowed. (3) **Nightly hook** once per local day after 03:00 (skipped if a run finished within the last 20 h). (4) **Weekly "Monday" hook** once per scoring period, after every game of the week is final in game_lines; that is usually Tuesday early, after MNF. Hooks start empty and later units register into them (PROJ-04, TELLS-01 nightly refit, HYPO-01). Heavy hooks run as child processes (the `spawnSync` pattern at refresh-live-data.mjs:111-190), so polling never waits on a refit. (5) **Single-instance lock:** an `O_EXCL` lockfile holding pid + start time + host. A stale-pid check (`kill(pid,0)`) takes over a lock only if its holder is dead; a second copy exits non-zero with "already running pid N". (6) **Heartbeat:** a `recordSync('engine_daemon', …)` row each tick, so the Data Health page shows it with no UI work. (7) **Launcher:** `~/gridiron-local/engine.sh` (local, not in the repo, the same shape as refresh.sh: COPY DB, paid keys blanked except the JEV-01 gateway when Nick enables it), `exec node scripts/engine-daemon.mjs --loop 600`. | ENGINE-00b-b | "Every update is versioned" + "Drift and health monitors" | (1) **Producer versions:** a registry row per (producer, version, code_sha, params_hash, status = active, shadow, retired or fallback). `getState` serves the **active** version. `scripts/engine-rollback.mjs --producer P --to vN` flips the pointer and appends a `producer_rollback` event; it deletes no rows. (2) **Baseline per critical field:** every field that feeds a served number names a registered baseline producer. For example, this week's points uses ESPN's number, and P(accept) uses the `acceptanceBand` (trade-acceptance.js:142) version in force when the learner shipped. The baseline writes a declared `baseline_of` slot, **not a second writer of the field**. (3) **Drift monitor** (a nightly hook plus a cheap per-tick check): it grades the live producer against the baseline on the same settled outcomes, using `gradeDecisions` (baseline-gate.js:106) for decisions and a paired proper score (log score or MAE) for distributions. **Fallback rule (pre-registered):** n ≥ 30 graded pairs AND the upper bound of the one-sided 90% interval of (live − baseline) < 0. Then the served field switches to the baseline, and a reason_chain contribution `{source:'health_monitor', text:'fell back: live below baseline, n=…'}` is added. **Recovery needs a fresh window** with the lower bound > 0 (hysteresis), so it never flip-flops. ## HYPO-01: the AND REASONS hypothesis loop

| ID | plan item | goal | files | acceptance | deps |
|---|---|---|---|---|---|
| HYPO-01a | AND REASONS "Hypothesis loop" (propose) | (1) **Surprise detector** (an `onEvent` learner). For each settled prediction, surprisal s = −log p(outcome) under the **served** distribution for that as_of. The prediction types are a P(accept) vs the decision, a projection vs the actual (weekly_prediction_snapshots), activity vs a waiver spree, and a PROJ-04 autopsy row's non-luck miss. It is a surprise if s > the 95th percentile of s for that stream on the walk-forward calibration window (a threshold per stream, refit nightly). A `surprise` event is appended with the triggering event_ids. (2) **Reasoner:** in batches (the nightly hook), send each surprise's evidence pack (the relevant `getState` rows with their reason chains, and the surrounding events, all as of the surprise) **through the JEV-01a gateway only**. The reasoner returns 1-5 candidate explanations, each a **feature spec in a fixed JSON grammar**: entity, event_types, window, aggregation, comparator, predicted sign and target stream. A whitelisted compiler turns the spec into an as-of query over engine_events. **No generated code is executed.** (3) **Pre-registration:** each candidate is hashed and appended as a `hypothesis_registered` event **before** any test reads data. Candidates are stored as engine_state (entity `hypothesis`, one producer) with a reason_chain back to the surprise | `server/services/engine/hypo/{surprise,reasoner,spec-grammar,compile}.js` (new); registers on ENGINE-00b-a's hooks; calls JEV-01a's gateway client; migration **080 (placeholder)**, only if ENGINE-00a's state cannot hold hypothesis rows; tests with a **stubbed gateway (no paid calls in tests)** | **RED:** (1) the compiler rejects any spec outside the grammar, and a spec that reads after its as_of fails; (2) the registration event precedes every test-read event for that hash (the check-prereg-order.mjs:68-95 idea applied to events); (3) with the gateway absent, candidates queue as `pending_reasoner` and the status says so (no silent skip); (4) the reasoner input contains no event after the surprise's as_of. **PRE:** on the 2024 replay the per-stream threshold flags 5% ± 1.5% of settled predictions (calibrated surprise rate) | ENGINE-00b-a, JEV-01a, ENGINE-00a |
| HYPO-01b | "the data decides" (screen + keep) + Autopsy hooks | (1) **History test**, walk-forward: fit on 2021-22, test 2023, refit, test 2024 (Sleeper history for manager tells, local 2021-25 for players). **The events that triggered the surprise are excluded** (no double-dipping). (2) **Screen:** the same sign in every test season AND it survives **online FDR (LORD++ at q=0.10)** across **every hypothesis ever tested**. Hypotheses arrive over time, so a per-batch BH would leak. The mass_test_harness q is kept. (3) **Live:** survivors go to `shadow` for the forward window (pre-registered n per stream) and are promoted only if the forward sign holds and they are non-inferior to the stream's baseline (ENGINE-00b-b monitor). Losers are marked `dead` and go to the R&D queue as a row. (4) **Kept means handed over, not served here:** a survivor becomes a candidate row in TELLS-01a's intake (manager tells) or the owning PROJ producer's feature list. **HYPO-01 never writes P(accept) or points itself** (one writer). (5) **Autopsy hooks:** PROJ-04-a already owns the causal split (week-postmortem.js:44). HYPO-01b adds only (a) autopsy non-luck links as surprise inputs and (b) the "fix the engine is making" line: the hypothesis ids opened plus any fallback from the monitor, written as a reason_chain contribution on the autopsy row via an onEvent hook, **without editing week-postmortem.js** | `server/services/engine/hypo/{screen,online-fdr,promote}.js` (new); a JS port of the BH/LORD math, a pure function with a test vector from atom_drift.py:71; TELLS-01a intake (read its spec); tests | **PRE:** (1) planted-signal simulation: of 200 null specs + 10 planted true effects on the replay, the screen keeps ≥ 8/10 true and the false-keep proportion ≤ 0.10 over 1,000 seeds; (2) the rule, q and forward n are committed in docs/evidence before the first live hypothesis. **RED:** (3) the LORD++ port matches a reference vector exactly; (4) a spec whose sign flips in one season is dropped; (5) a survivor creates an intake row and no served-field write (grep plus runtime registry assert); (6) the autopsy "fix" line lists the opened hypothesis ids | HYPO-01a, PROJ-04-a (autopsy rows), TELLS-01a (intake), ENGINE-00b-b (baseline monitor) |
