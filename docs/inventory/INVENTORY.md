### How this count was arrived at, including the two wrong answers

The phantom-table figure moved twice before it settled, and both moves are recorded
here rather than presenting the final number as if it were the first.

**1 →** the first pass hand-marked a single table, on the reading that the creation
bucket could not be derived. That was wrong for a specific reason: it read
`created_via`, which is only a resolved-from pointer for definition-indirected
creates and is null by design almost everywhere. The bucket is `created_by`, and it
is populated for every table.

**→ 24** once the sweep ran on the right field. But that conflated two different
things.

**→ 7** after separating tables that live in ANOTHER database. For the chat corpus,
the sleeper-history DB and the jev crawl DBs, "no migration creates it" is expected
rather than a defect: those databases are not migration-managed and their own sync
builds their schema. Seventeen tables moved out on that basis, and the same fix
corrected a measurement bug — app-DB row counts were being read for tables that are
not in the app DB, which says nothing about them.

Each move was toward what the map actually proves. The number to act on is 7.

`referenced_but_never_created` is a table-only status, not one of the five component
statuses. A phantom table — named in SQL, read across the app, created only by a
hand-run script or a test fixture and by no migration — is absent in any database
where that script never ran, production included. It is not `silently_broken` (that is
a code path returning success while reading nothing; a table is not a code path), not
`dead` (it is read from everywhere), and not `half_done` (the reader is finished; the
CREATE is what is missing). Forcing it into one of the five would mislabel it, so it
carries its own name.
