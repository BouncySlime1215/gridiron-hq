# FIX-HOLD-01: the failed-slate hold is keyed on the call config (2026-09-24)

## Audit (extend, not build)
- Producer: `server/services/trade-proposals.js` `proposalsFor` → `failureKeyFor`. The one writer and the one reader of the hold are both in `proposalsFor`; the route (`server/routes/trades.js:784`) passes `liveCaller(callClaude)` and is unchanged.
- Defect: the hold key was `<slate hash>.failed`. After the effort/maxTokens fix (#213), a slate held as "ran out of output room" under maxTokens 4,000 kept being served from the hold for up to `FAILED_SLATE_TTL_MS` (6h), because nothing about the call was in the key.

## Change
- `PROPOSALS_CALL_CONFIG` (model, maxTokens, effort) is now the one place the call is configured. `liveCaller(callClaude, config = PROPOSALS_CALL_CONFIG)` sends it and exposes it as `call.config`.
- `failureKeyFor(key, config)` → `<slate hash>.failed.<sha256(model, maxTokens, effort)[0..16]>`. `proposalsFor` reads and writes the hold under that key. A caller with no `config` hashes all-null, so injected test callers still get a hold.
- Old `<hash>.failed` rows are orphaned, not migrated: each held slate is retried once on deploy, which is the intent. No schema change.

## RED / GREEN
- RED `4746111` "test: RED failed-slate hold survives a change to the call config": `not ok 57` (FIX-HOLD-01: config A truncates, config B must make a fresh call) and `not ok 58` (each of model / maxTokens / effort breaks the hold alone). 57 pass, 2 fail.
- GREEN `39f3d44`: trade-proposals 59/59. trade-proposals + llm-budget-per-league + trade-brain-surface + trade-outcomes-route: 88/88.
- Existing test "a remembered failure from an older parser version is ignored" wrote to the literal `${key}.failed`; after the rekey that would have passed vacuously (wrong key, not the version check). It now writes to `failureKeyFor(key, PROPOSALS_CALL_CONFIG)`.
- Mutants (tests at GREEN): M1 hash a constant instead of the config → fail 2 (killed). M2 drop `effort` from the hash → fail 1 (killed). M3 drop `model` from the hash → fail 1 (killed).

## Nick's five questions
1. Well built? One key function changed, one config constant extracted; the hold keeps its TTL, slate hash and parser-version bounds.
2. Stats or made up? Not statistical.
3. How we know: RED/GREEN above plus three killed mutants. Forward check: the next config change to `PROPOSALS_CALL_CONFIG` should show a fresh `ai_usage` row for a league whose slate was held.
4. Pointed anywhere else? Only `proposalsFor`'s hold. The answer cache key (`cacheKeyFor`) is unchanged, so successful answers are still reused across a config change.
5. How it unifies: the call config lives in one constant, read by both the caller and the hold key.
