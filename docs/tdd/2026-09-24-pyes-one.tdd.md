# PYES-ONE: one module serves P(yes) to every caller

ONE-PLAN.md 4 item 6 and night 3: `league-adapter.mjs` (War Room) and
`trade-engine.js` (Trade Lab / Coach / trade cards) each call
`trade-acceptance.js#acceptanceBand` directly, so a change to the served P(yes)
(PYES-BASELINE, #319) reaches one screen and not the other.

## Pre-registration (written before any code on this branch)

- **Metric 1 (one module).** Count of production files that import
  `acceptanceBand` other than `server/services/p-yes.js` and the E1 grader's
  replay (`server/services/eval/e1-league.js`, which must keep scoring the clone
  as of each offer). Before: `league-adapter.mjs`, `trade-engine.js`,
  `negotiate-engine.js`, `acq-flip-proto.mjs`. Pass bar: **0**.
- **Metric 2 (flag off is byte-identical).** With `GRIDIRON_PYES_BASELINE`
  unset, the acceptance object each caller serves deep-equals
  `acceptanceBand`'s output for the same inputs. Pass bar: equal on every
  fixture case.
- **Metric 3 (flag on, same number in both callers).** With the flag `=1` and a
  fixture decided-offer table, the served p for each responder equals
  `eval/e1.js#activityBaseline` for that responder row by row, through the
  War Room `priceStep` shape AND the trade-engine acceptance shape. Pass bar:
  equal to 1e-12 on every row.
- **Label.** Flag on, a served step's `p_yes.source` is `activity.accept`
  ("activity baseline (E1 pending)"), and the card's confidence text says ladder
  rungs differ by Nick's gain, not by P(yes). Flag off: `clone.accept`, text
  unchanged.

**What fails it:** any production importer of `acceptanceBand` left outside
the module; any byte difference with the flag off; any row where the two
callers serve different p with the flag on.

Default: **off** (shadow). Nothing Nick sees moves until the flag is set after
local measurement.
