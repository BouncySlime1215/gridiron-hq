# LAST-GOOD: after a failed refresh, serve the last good plan and block sending

2026-09-26. Batch D item 53 (OFFLINE / LAST-GOOD MODE, research E6 fail-safe). Off `main` `3ac1016b`.

When a refresh step fails, the producer's atomic write already leaves the previous
`plans.json` in place, so the War Room keeps serving the old plan. Nothing on screen
says the plan is now older than the failed refresh, and "I sent it" still records a
send built on it. The loop already records every step's outcome in `sync_log`
(`scheduler.js#record`); nothing in the War Room reads it.

## Pre-registration (written before the GREEN commit)

Flag `GRIDIRON_LAST_GOOD=1` (own flag, off by default, never preview mode). Refresh
steps: the ESPN league sync (`league_rosters`) and the plan refresh (`warroom_plans`).

- **B1 (no collateral, flag off).** The War Room view is deep-equal to main's, and
  neither send route reads `sync_log`, even with a failed row present.
  **Fails it:** any `last_good` key, any read, any status change.
- **B2 (last good served, flag on).** With a failed refresh step, every plan section
  is served deep-equal to the flag-off view, plus `last_good` with `as_of` equal to
  the plans' `generated_at` and `send_blocked: true`. **Fails it:** a hidden or
  changed section, or an `as_of` other than the plans' own time.
- **B3 (sending blocked).** With a failed step, `POST /api/warroom/:id/requests`
  kind `offer.sent` and `POST /api/warroom/:id/negotiations` answer 409 with the
  reason and write no row. **Pass bar:** 0 rows written.
- **B4 (clears on success).** A later successful row for every step: no
  `last_good`, both routes pass the gate.
- **B5 (fail closed).** A step `running` for more than 90 min, or a `sync_log` that
  cannot be read, blocks. A step with no row at all is no evidence and does not.
- **B6 (no dev text).** The reason names no job id, table, path or env variable.
- **Served numbers.** None move. The unit only labels and blocks.
