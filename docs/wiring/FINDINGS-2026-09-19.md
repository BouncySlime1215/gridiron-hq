# What the wiring map found — 2026-09-19

Generated by `node scripts/wiring-map.mjs`, then read by hand. The map itself
is in `WIRING-MAP.md` (this branch) and `WIRING-MAP-integration.md` (every open
pull request merged together locally — see **What was mapped** at the bottom).

Two families, because they are different problems with different fixes.

- **MISSING FEED** — a surface depends on something nothing produces. This is
  the one that hurts users: the page still renders. It renders a constant, a
  default or an empty list, and it looks fine.
- **ORPHAN** — something produced that reaches no surface. Wasted work.

Betting rows are mapped and tagged `betting`. Out of scope for work, in scope
for knowing.

## Corrected after review — read this first

The first run of this reported five tables as "read by the app and written by
nothing", four of which were **a false alarm**, and the Trade Brain thread
caught it. `messages`, `jev_chat_signals`, `manager_chat_profile` and
`manager_player_sentiment` are not in the app's database at all. They are
Nick's iMessage corpus: a separate SQLite file opened read-only through
`chatDbPath()` / `messagesDbPath()`, built on his Mac and delivered whole
through `POST /api/league-chat/upload`, which refuses a corpus whose `messages`
table is empty. Both consuming surfaces already refuse and name the gap when it
is absent, with tests written around exactly that.

The tool was pooling two databases into one namespace. It now reads which
handle each query was given and reports those tables as
`table-in-another-database` — explicitly **not** a missing feed. The general
lesson is in the tool's own output now: the difference between "no writer" and
"broken" is the whole value of this thing, and it got that difference wrong
once. A tool that cries wolf gets switched off, and its true findings go with
it.

A second correction, from the end-to-end thread: `player-week-engine.js:190`
reads the availability tables inside `applyRedistribution`, which only runs
when `redistributeVolume` is true — a parameter that defaults to false and that
nothing outside `scripts/eval-redistribution.mjs` ever sets. Real as code,
false as behaviour. Verified independently before changing anything. The map
now reports these as `edge-behind-an-off-flag` rather than drawing them as live.

it fails on a NEW gap, not on debt that predates it.

## STALENESS (3)

A third edge type, suggested by the end-to-end thread and derivable: whether a
consumer can *see* a change to the store it depends on. Two modules can read
the same table and behave in opposite ways.

- `routes/model.js` memoises three values under **constant** keys —
  `'avail'`, `'handcuffs'`, `'cascades'` — in a module that reads ten tables.
  There is no input in the key at all, so the first answer the process computes
  is served until the process ends. `'avail'` is `availability()`: write the
  availability fit and that endpoint keeps serving pre-fit numbers.
  `leagues.js:222` documents the hazard and works around it by calling
  `clearModelCache()` on league sync.
- `nfl-weekly-feature-store-v2.js` (`'nflverse:participation'`) and
  `preseason-model.js` (`'names'`, `'bio'`) are the same shape.

By contrast `trade-engine.js:224-225` names both availability tables in its
cache fingerprint stamped on `fitted_at`, so it self-invalidates. On a
data-flow map those two look identical. The rule only reports constant keys,
because a key built from request arguments is a judgement call and a check that
reports judgement calls gets switched off.

## Running it

    npm run map:wiring                                  # write docs/wiring/*
    node scripts/wiring-map.mjs --findings              # findings to stdout
    node scripts/wiring-map.mjs --blast <table|module>  # if this changes, what moves
    npm run check:wiring                                # exit 1 on any missing feed

`--check` gates on the missing-feed family only. Orphans are reported and do
not fail: deleting one is a judgement call, and a gate that fails on judgement
calls gets switched off.

## What the map cannot see

Written down so nobody trusts it further than it goes.

- **Value-level dependencies.** `league_member_identity` has a writer reachable
  from a route, so the map calls it fed. It is not: a row is only usable once
  its `confidence` is `confirmed`, and only a person can set that. This is in
  `annotations.json` because it cannot be derived.
- **Dynamic table or module names.** A table referenced only through an
  interpolated identifier is invisible.
- **Hop distance is not call graph.** A route three hops from a module imports
  something that imports it; it does not prove the route calls it.
- **Route matching is by shape**, so `/a/:id` and `/a/:other` are the same path.
